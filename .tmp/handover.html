1Executive Overview

The Kiddies Town ECD & Academy Portal is a custom-built, fully responsive web application that digitises the core operations of the school. It replaces ad-hoc paper registers, verbal updates, and scattered messaging with a single secure platform that serves three audiences through dedicated portals:

  • Parents — real-time visibility of their child's attendance, weekly learning themes, progress reports, fee statements and receipts, school events with RSVP, and a direct messaging channel to staff.
  • Teachers — daily attendance capture, milestone and progress assessment across ten developmental indicators, classroom journal publishing, theme planning, and parent communication.
  • The Principal / Administrator — centralised oversight of enrolments, learners, staff, transport routes, medical profiles, finances, bulk parent communications, emergency broadcasts, and a full audit trail.

The platform is built on a modern, widely supported technology stack (React, TypeScript, Node.js/Express, PostgreSQL) that is inexpensive to host and straightforward for any competent web developer to maintain. Data protection is a first-class concern: access is role-restricted, passwords are cryptographically hashed, every significant write action is recorded in an audit log, and data structures were designed around South Africa's POPIA obligations.

Business Value at a Glance One system for enrolment → attendance → assessment → reporting → billing → communication. Parents self-serve routine questions; teachers capture evidence once; the principal sees live school-wide statistics without compiling spreadsheets.

In Scope of This Handover

  • All three dashboards plus the public landing page and online enrolment wizard.
  • REST API (v2) with authentication, role-based access control, validation, rate limiting, and audit logging.
  • Database schema (PostgreSQL / Neon serverless) with a local JSON-file fallback mode for demonstrations.
  • Dynamically generated PDF documents (parent developmental guide).
  • Source code repository layout, build pipeline, deployment procedure, and operational runbook.

Out of Scope

  • Payment gateway integration (payments are currently captured as ledger records/receipts; no card acquiring).
  • Automated off-site backups and monitoring/alerting services (recommendations in Section 11).
  • Content such as photographs, policies, and fee values — these remain editable data owned by the school.

3User Guide

3.1  Accessing the System & Signing In

  1. Open the portal address in any modern browser (Chrome, Edge, Firefox, Safari — desktop or mobile). The landing page is public.
  2. Select Login and enter your school email address and password.
  3. Select the profile/role you are signing in as (Parent, Teacher, or Principal/Admin). The role must match the account's assigned role or sign-in is refused.
  4. You are taken straight to your role's dashboard. Sessions expire after 15 minutes of token lifetime; the app renews automatically while in use.
Password Guidance On first production use, each seeded account holder should change their temporary password immediately (see Section 4 for the seeded credential list). Passwords are never displayed by the system to anyone, including administrators.

3.5  Online Enrolment Wizard

Public-facing, no login required. Applications proceed through six validated steps:

  1. Child Particulars — names, date of birth, ID number, gender, home language, religion, requested grade/class.
  2. Parent Details — contacts, addresses, marital status, guardianship ("child lives with").
  3. Medical Profile — allergies, conditions, medication, doctor details.
  4. Transport Details — shuttle/CBD pick-up requirements.
  5. Consents — POPIA information-processing consents and school policy acceptance.
  6. Document Upload — supporting documents (birth records, immunisation cards, etc.).

Every step is validated inline before progression; incomplete submissions cannot advance. Submitted applications appear instantly in the Principal Admin Center's enrolment pipeline with a reference status.

5.3  Authentication Flow

  1. User submits email + password + selected role to POST /api/auth/login. The role must match the stored account role.
  2. Password verified against its bcrypt hash (cost factor 12). A legacy plaintext-comparison fallback exists in the login path for pre-migration accounts (flagged in Section 10).
  3. Server issues a signed HS256 access token (15 min, issuer kiddies-town, secret JWT_SECRET) and a refresh token (7 days, secret JWT_REFRESH_SECRET). Both are returned in the JSON response body.
  4. The client keeps the access token in browser localStorage and attaches it as a Bearer header. The refresh token is not persisted client-side; renewal uses POST /api/auth/refresh-token.
  5. Each protected request passes requireAuth(); write endpoints additionally pass requireRole('parent'|'teacher'|'admin'). Unauthenticated visitors receive read-only guest data (public themes, events, journal only).

5.4  Request Pipeline (middleware order)

helmet (security headers; CSP relaxed in dev)
→ CORS allow-list (credentials, CORS_ORIGIN)
→ compression
→ body parsing (JSON & urlencoded, 10 MB limit)
→ rate limiting (general API: 100 req / 15 min · auth endpoints: 10 req / 15 min)
→ JWT bearer authentication (optional guest fallback, role 'guest')
→ RBAC role guard (per-route)
→ Zod schema validation (request bodies)
→ audit-log middleware (records writes)
→ route handlers → central error handler (always last)

5.5  Data Modes

  • Cloud mode — when DATABASE_URL is set, the server connects to PostgreSQL (Neon), bootstraps all tables/enums on start-up, and seeds baseline content if empty. This is the production mode.
  • Local file mode — without DATABASE_URL, all reads/writes map to data_store.json, seeded from mock data. Ideal for demos/training on a laptop; not sized for production volume. The file contains PII and is git-ignored by policy.

8.3  Deployment Procedure (typical)

  1. Provision a PostgreSQL instance (e.g., Neon) and copy its connection string into DATABASE_URL.
  2. Set strong JWT_SECRET / JWT_REFRESH_SECRET values and NODE_ENV=production, CORS_ORIGIN=https://your-domain.
  3. npm ci && npm run build on the host (or build in CI and ship dist/).
  4. npm start under a process manager (pm2, systemd, Docker, or platform runtime). The server bootstraps the schema automatically on first connect.
  5. Verify GET /api/health, then log in with the admin account and change the seeded password.

A ready-made production bundle ships in dist/ and can be started immediately with npm start (plus a completed .env).

9Security & POPIA Compliance

9.1  Controls Implemented

  • Authentication & sessions — short-lived JWT access tokens, refresh rotation endpoint, role-matched login.
  • Password storage — bcrypt hashing (cost 12); hashes are never returned by any endpoint.
  • Authorisation — every write endpoint declares its permitted roles; deletion of learners is admin-only; medical data sits behind admin access.
  • Input hardening — Zod schema validation on all mutating requests; parameterised SQL via Drizzle ORM (mitigates injection).
  • Transport & headers — helmet security headers; enable HTTPS at the hosting layer (recommended reverse proxy / platform TLS).
  • Abuse prevention — general API limit 100 req/15 min; strict 10 req/15 min limiter on authentication endpoints.
  • Data minimisation for guests — unauthenticated visitors see only public curriculum/event/journal content; no learner identities.
  • Auditability — kt_audit_logs records user, action, payload and timestamp for significant writes.
  • PII hygiene — data_store.json and .env are git-ignored; documents advise against committing PII.

9.2  POPIA Alignment

ObligationHow the platform addresses it
Lawful processing & consentEnrolment wizard captures explicit POPIA information-processing consents (Step 5) before an application is accepted.
MinimalityOnly ECD-operational fields are collected; role-scoped feeds mean each user sees only what they need.
Security safeguardsHashed credentials, RBAC, rate limiting, validation, audit trail (§9.1).
Children's informationChild identities, birth records, addresses and phone numbers are never publicly indexed or exposed to unauthenticated visitors.
Operator accountabilityAudit logs support internal investigations and evidence of processing activities.
Data subject participationParents view and correct their household profile via the Parent Hub; export/deletion requests can be fulfilled by the administrator with developer assistance.
Residual Responsibility POPIA compliance is shared: the school remains the responsible party for lawful grounds, retention limits, and breach-notification duties. Ensure the hosting provider agreement covers data processing, and schedule periodic review of the audit log and user accounts.

10Known Limitations & Handover Notes

#ItemDetail / Recommendation
1Seeded passwords are trivialparent/teacher/admin defaults exist for training. Change all three before admitting real learner data.
2Legacy plaintext comparison fallback in loginThe login path retains a fallback comparison for pre-migration accounts alongside the bcrypt check. Recommend migrating any remaining accounts and removing the fallback (single-file change in the auth controller).

8Windows path quirk workaroundscripts/dev.mjs exists because tsx mis-handles the space in the folder path ("New folder") on Windows; keep using npm run dev rather than invoking tsx directly.

11.2  Priority Recommendations After Handover

  1. Change all three seeded passwords and distribute private credentials to real staff.
  2. Configure automated backups (Neon point-in-time recovery or scheduled dumps) and store copies outside the server.
  3. Enable HTTPS end-to-end and set CORS_ORIGIN/APP_URL to the production domain.
  4. Remove the legacy plaintext login fallback once all accounts are confirmed hashed (item 10.2).
  5. Adopt uptime monitoring against /api/health with alerting to the principal's mailbox.
  6. Archive or delete the legacy files (server.ts, App.legacy.tsx) after one month of stable operation.
